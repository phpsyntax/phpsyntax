# PhpSyntax internals

How the syntax layer works: the facts an agent or a contributor needs before touching the lexer, the grammar, the nodes or the mutation API. The catalog of nodes is not here; `docs/reference/nodes.md` is generated from `grammar/nodes.php` and the node classes.

The library has no dependencies and never imports Nette, php-parser or anything from `vendor/`: `composer.json` requires PHP and `ext-tokenizer` and nothing else, and what the tests and the tools need is `require-dev`. Everything under `PhpSyntax` is public API but for what says `@internal`, so a tool built on the library may reach for any of it. What such a tool uses stays public, and a helper only the classes of the library share is `@internal` with that reason (`TokenIndex::countLineEndings()`), which is how the surface is decided for a new method too.

## Tokens and trivia

The lexer (`PhpSyntax\Lexer\Lexer`) turns `PhpToken::tokenize()` output into significant tokens; whitespace, comments and open tags become `Trivia` attached to tokens:

- **Trailing trivia** of a token is everything after it up to and including the first end of line. **Leading trivia** of the next token is everything else (blank lines, indentation, comments on their own lines, doc comments). Whitespace is split into `Whitespace` runs and single `EndOfLine` pieces (`"\n"`, `"\r\n"` or a lone `"\r"`). The line ending of the line above belongs to the token that ends it, so an `EndOfLine` among leading trivia is a blank line or the end of a comment's own line: an indented token below one blank line leads with `[EndOfLine, Whitespace]`, one directly below the previous line with `[Whitespace]` alone.
- Exceptions: an `OpenTag` trivia (`<?php` with its mandatory whitespace) is always leading trivia of the following token, and everything after it too; the final `EndOfFile` token has only leading trivia, never trailing; a token whose text ends with a newline (`CloseTag`, a heredoc start) ends its line the same way an `EndOfLine` does.
- `<?php` is not a token. `?>` is a token of kind `CloseTag` that keeps the newline PHP swallows after it, and the parser sees it as `;`; after a terminated statement it forms an `EmptyStatementNode`. `<?=` is a token of kind `OpenTagWithEcho` seen as `echo`. `Token::isSemicolon()` and `isOpenTagWithEcho()` cover these cases.
- Whitespace that PHP counts as part of a token stays in its text: inline HTML, `T_ENCAPSED_AND_WHITESPACE`, heredoc delimiters (the closing one keeps its indentation), casts like `( int )`.
- Trivia inside string interpolation (`"{$a /* c */ }"`) carry `inInterpolation = true`; the token helpers refuse to change them because inside a string whitespace can change what is read: `"${a}"` interpolates `$a`, `"${a }"` the variable the constant `a` names.
- A BOM or a hashbang line is inline HTML, as PHP sees it; `InlineHtmlNode::isPreamble()` tells whether that is all the text is, which is what makes a file pure PHP. A single-line comment never contains its newline, but it does contain trailing spaces before it.
- Token ids differ between PHP builds; `TokenKind::HostConstants` maps them by constant name. A token of a single character has the ordinal of that character as its kind (`ord(';')`), not a named constant of `TokenKind`. A keyword is named by the word itself (`TokenKind::If`), except `ClassKeyword`, `class` being reserved for `::class`, and `NamespaceKeyword`, which PHP reserves from 8.6. Constants missing on the host are never defined at runtime (php-parser does that), because a library must not have that global side effect; instead `TokenKind` carries four raw kinds (`Whitespace`, `Comment`, `DocComment`, `OpenTag`) that live only between the tokenizer and trivia folding, so the emulators work over one uniform list of tokens. Syntax of PHP 8.5 on an older runtime is emulated by rewriting the raw token stream (`Lexer\Emulators`).

## Round trip

`Printer::print(new Parser()->parse($code)) === $code` byte for byte for any input PHP accepts, including BOM, hashbang, CR/CRLF, close tags, inline HTML and `__halt_compiler()` data. It is the invariant every change to the lexer, the grammar, the nodes or the printer must keep; the tests run it over the committed corpus (`tests/corpus/`) and, with `PHPSYNTAX_CORPUS` set, over an external tree. The printer is a concatenation and has no logic of its own, so what a tool changes in the trivia and the nodes is exactly what the text gets. `Printer::print()` and `Printer::printText()` (the text without the outer edges, which `Node::$text` reads) take a substitute, `fn(Token): ?string`, printed in place of the text of a token while the trivia and the tree stay as they are: how a tool shows code with changes it has not made to the tree.

## Parser and generated files

The parser is an LALR(1) driver over tables generated by phpyacc from `grammar/php.y`, a fork of the nikic/php-parser grammar with the PHP 7 branch and the error-recovery productions removed. Productions are never changed, only their semantic actions. `composer compile-grammar` regenerates `src/ParserData.php`, `src/TokenKind.php` and `src/LayoutData.php` from `grammar/php.y` and `grammar/nodes.php`, and in every node class the `Slots` constant and the constructor; the output is committed, so a change to the schema and a rebuild belong to the same commit. A file generated whole says so with `@generated` in its header.

A node class is a handwritten file whose two generated members the generator replaces in place: it finds the `Slots` line and the constructor (from `public function __construct(` to the first `}` on a line of its own) by the shape it writes them in, and fails when it finds either zero or several times, so a class never falls behind the schema in silence. The schema (`grammar/nodes.php`) holds only the slots of a class, the layout roles that differ from the convention and `manual` for a class whose `Slots` and constructor are handwritten too (`FileNode`, the lists, `ModifiersNode`), which the generator leaves alone; the description, the parent, the interfaces and the methods belong to the class, and `docs/reference/nodes.md` reads them from it by reflection. The generator is deliberately simple, because the schema changes once a year with a PHP version and a person is at the keyboard: a missing class is written as a skeleton to complete, a missing import is reported and added by hand, a file the schema does not know is reported and never deleted. The procedure for a new PHP version:

1. Add the tokens and productions to `grammar/php.y` with their actions, and the slots of new or changed nodes to `grammar/nodes.php`.
2. `composer compile-grammar`; fix what it reports: complete the skeleton of a new class (docblock, parent, interfaces, methods), add the imports it names, delete a class that is gone; the code style of `dresscode.neon` always runs over the output before it is committed, so the generator is not required to reproduce the committed files, and a bare rebuild differs from them.
3. `composer tester` with new dump fixtures in `tests/PhpSyntax/Parser/dump/`, then `composer phpstan`, `composer verify-examples` and `composer reference`; PHPStan analyses `examples/` too, so an API that changes is changed there as well.

- The token declarations are in the header of `php.y`, so there is no separate token grammar; `TokenKind` is generated from that header. phpyacc must report exactly the two shift/reduce conflicts of the dangling else that `%expect` declares, and a change in that number means the grammar was altered, not just its actions. `ParserData.php` is analysed by PHPStan like the rest, with one ignore for the node constructors its actions call: an action builds a list from the item its production has, while the slot is typed by every kind that may stand in it. What its actions put on the untyped value stack is guarded by the grammar, the coverage check and the round trip instead.
- Every grammar alternative with two or more symbols must have an action that uses every symbol, otherwise tokens would drop out of the tree; the build fails on such an alternative. A single symbol passes through, an empty alternative yields `null`.
- Actions may put plain arrays of slot values on the value stack (tails of alternative syntax, optional pairs such as `: type`); they are spread into the node constructor and never leave the parser.
- After parsing, statements following `namespace A;` are nested into that `NamespaceNode`, so every namespace has its statements as children; only `__halt_compiler()` stays outside.
- The data after `__halt_compiler();` is a token in `HaltCompilerNode::$data`.
- `Parser::parseFragment()` parses a piece of code into a node of the class given, inside the code such a node stands in: the wrappers name a kind each (`ExpressionNode`, `StatementNode`, `MemberNode`, `ParameterNode`, `ArgumentNode`, `ArrayItemNode`, `UseItemNode`...), and a class deriving from one of them is parsed in the same wrapper. The node comes back detached, with empty trivia on its edges and without original positions, and what leaves something over is refused: the node has to reach from the first token after the prefix to the last one before the suffix, which is how `$a, $b` given as one parameter is caught. `parseExpression()`, `parseStatement()`, `parseType()` and `parseName()` are its typed shortcuts. This is how a new node is built: a node constructor is `@internal`, its parameters following the slots of a grammar the next version of PHP may extend. A name, an identifier and a string literal are also made from their text or value (`NameNode::fromText()`, `IdentifierNode::fromText()`, `StringNode::fromValue()`), and a `Token` and a `Trivia` are constructed directly. What is put together from nodes already at hand has a factory `of()`, because a text cannot hold them: a call (`FunctionCallNode`, `MethodCallNode`, `StaticMethodCallNode`, `NewNode`), a one-line `ArgumentListNode` of values, a `BinaryOpNode` of two operands and the operator as text, and a `ParenthesizedNode`. A factory makes the tokens of the operators and the delimiters, the nodes it is given lose the trivia on their edges, and what a call is made on or an operator is given stands in parentheses where it could not stand there bare (`(new Foo)->bar()`, `($a->b)()`, `($a ?? $b) . $c`), by the answer of `ParenthesizedNode::isRedundant()`, so that the result is what the parser would return for its text.
- A `ParseException` says where in the source the error is with `$sourceLine`, `$sourceColumn` and `$sourceOffset`, told apart from the `getLine()` and `getFile()` of the exception itself. An error of a fragment is told in its terms: the position is counted in the fragment, and a token of the wrapper never reaches the message, the error beyond the fragment being `Unexpected end of the fragment`. An unterminated string, heredoc or shell command is refused by the lexer where it starts, the parser would only reach the end of the file.

## Exception messages

An exception is read by the author of a tool who parsed a fragment or wrote into a tree, with the stack trace beside it. It is one sentence, capitalized, ending with a period, that says what the call met, and what was expected where that is not evident; the refusing API is named only where the trace does not show it, as in the index, which finds a broken tree later than the write that broke it. A remedy may follow after a semicolon, as a statement naming the API that gives it (`a copy comes from withoutEdgeTrivia()`), never as a command. The subject is the thing refused, `The node`, `The trivia`, a token by its text (`Token '$x'`); a value the caller passed goes in single quotes, a class the library names itself and a method stay bare.

A `ParseException` of the grammar follows the syntax errors of PHP, `Unexpected <what>, expecting <list>` and `Unterminated <what>`, with no period, because a caller appends the position. The tokens expected are named the way PHP names them (`identifier`, `variable`, `'{'`), never by the lexer constant (`Parser::TokenNames`). An invariant of the parser itself is a `LogicException` for the maintainer and takes the form alone.

## Tree

- Every node class ends with `Node`; slots are named by role (`ifKeyword`, `openParen`, `semicolon`, `condition`, `body`), paired delimiters are always `open*`/`close*`, lists are plural or bear the keyword that introduces them (`extends`, `implements`). Every token of the source has a slot or a place in a list, so the order and number of children are not part of the API, only the slot names. Whoever names a slot instead of reaching for it writes the name as a string (`'openParen'`), and the `Slots` constant of the class is what such a name is checked against, which is how a table of them is verified at startup instead of falling silent after a slot is renamed.
- A node is named by the word PHP itself writes, keyword or function (`IfNode`, `ThrowNode`, `ShellExecNode`, `HaltCompilerNode`), and by a noun where PHP writes no such word (`ArrayAccessNode`, `PropertyFetchNode`, `CombinedAssignmentNode`, `TernaryNode`); a bare verb is not a node name, and where the manual has a term for the construct, that term wins over the one other languages use, which is why a compound assignment is a combined one here.
- A slot says what stands in it, not what the reader could guess from the class. The target of a write is `target` and not `variable`, because it is any writable expression and `isWritable()` is the question asked of it; what a `switch` and a `match` compare against is `subject` and not `condition`, because it is not evaluated for truth; a `case` carries `value` and a `match` arm `values` for the same reason. Names of the API are written in full, a local variable may be abbreviated; the abbreviations left in the API are `paren` in `openParen`/`closeParen`, the delimiter having no one-word English name, `eol`, and `Op` in `BinaryOpNode` and its kin.
- Lists: `NodeList<T>` (statements, members, attribute groups) and `SeparatedNodeList<T>` (parameters, arguments, items, imports) with separator tokens between items and an optional trailing separator; `EmptyArrayItemNode` stands for nothing between two commas of a destructuring list. `ModifiersNode` holds modifier tokens in source order. All three are iterated and counted directly (`foreach ($call->arguments->items as $argument)`), and `getItems()` gives the same items as an array (`getTokens()` in `ModifiersNode`); the iteration is a snapshot, safe while the list is being mutated. A read-only helper over any list writes `@param NodeList<covariant Node>`, the type parameter being invariant. `ModifiersNode::$visibility` is null where no visibility is written, a parameter promoted by `readonly` or `private(set)` alone included, so whether a parameter declares a property is asked of `ParameterNode::isPromoted()`. Which argument of a call a parameter gets is `ArgumentListNode::findArgument()`: the one written with its name first, then the one at its position, a `?` placeholder holding a place without being an argument, and no position after an unpacked argument has an answer.
- The body of a control structure is a `StatementNode`, not necessarily a block; `else if` is an `ElseNode` whose body is an `IfNode`. The alternative syntax uses the same classes with `colon`, `statements`, `endKeyword` and `semicolon` slots instead of `body`. An import is one `UseNode` however it is written, the group form filling the `prefix`, `openBrace` and `closeBrace` slots the plain one leaves empty (`isGroup()`), and `UseItemNode::$fullName` is the name an item imports, the prefix of the group included. What an item imports is said by the statement it stands in, so an item is never moved from one statement to another but written anew by `UseNode::addImport()`, the way the statement writes its items.
- Destructuring is a `ListNode` whichever of its two spellings is used, the `listKeyword` being null for `[...]`, and so is a destructuring nested in one, however deep and whichever spelling either of them uses. A short array is built as an `ArrayNode` and turned into a `ListNode` where it stands as a target: the left of an assignment and the value of a `foreach`. An `ArrayNode` is therefore an array literal and never a destructuring. A `ListNode` is no expression, having no value of its own to answer for: it stands only where a target is written, which is what the slots `AssignmentNode::$target`, `ForeachNode::$value` and `ArrayItemNode::$value` say by holding `ExpressionNode|ListNode`, and a caller that asks a question of expressions there narrows first.
- Every scalar literal is a `ScalarNode`, whatever it is written with, so a question about literals is one `instanceof` and not a list of nine classes; `ExpressionNode::isRepeatableRead()` is one that asks it. Scalars keep their raw text (`IntegerNode::$token->text` is `0x1F`) and give the value it stands for as `$value`, with `$base` beside it for an integer and `$quote` for a string, and an integer literal beyond the integer range is a `FloatNode` whatever its base, because PHP reads it as a float, so not every integer written is an `IntegerNode`; `StringNode::setValue($value, ?$quote)` changes how a string is written without changing what it is; a heredoc answers `hasInterpolation()` before its `$value` can be read, and that value is the body outdented first and read for escapes afterwards, the indentation being physical while what `\n` makes is no line of the source to outdent, and an offset written without quotes inside an interpolated string is an `UnquotedStringNode`, so a string always has a delimiter to write a value with. `StringNode::fromValue()` goes the other way and writes a value as a literal. `true`, `false` and `null` are literals too (`BooleanNode`, `NullNode`), not constant fetches, although the grammar reads them as names: they keep the letter case and the leading backslash they are written with, and a qualified or relative name of the same spelling (`A\true`) stays a `ConstantFetchNode`, because that is the constant PHP would look up.
- Operators are one `BinaryOpNode`, `UnaryOpNode`, `PrefixOpNode`, `PostfixOpNode`, `CombinedAssignmentNode` with the operator token, or a `CastNode` with its `cast`, plain `=` being an `AssignmentNode` of its own, because the grammar takes a destructuring on the left of that one alone, and `++`/`--` are a `PrefixOpNode` or a `PostfixOpNode` rather than a unary operation, because the grammar takes a variable for them and any expression for `-` and `!`.
- Names are one `NameNode` with a token of any kind, including keywords the grammar accepts as names, and its `$text` is what is written there (writing it replaces the token with the kind the new name needs), `$parts`, `$shortName` and `$kind` take it apart and `$role` tells from its place in the tree whether it stands for a class, a function or a constant, classes and namespaces being one table of names in PHP, while `isDeclaration()` tells a name a use or namespace statement introduces from one that refers to something, and `isReference()` whether the name refers to a symbol at all: not a declaration, not self, static or parent, and not a builtin type where a type is written, which is what the resolver refuses. `equals()` compares the writing with a string, a constant exactly and anything else regardless of letter case, the leading backslash being part of the writing; whether two names mean one symbol is for `NameResolver`. What is written as an identifier instead (the name a declaration introduces, a member, a label, an alias, the name of a named argument) is an `IdentifierNode`, one token whose `$text` takes an identifier and nothing else. Either reads its text as `->text`, and the slot holding it is named by its role (`name`, `class`, `extends`, `method`, `label`).
- Class-like declarations (`ClassNode`, `InterfaceNode`, `TraitNode`, `EnumNode`, `AnonymousClassNode`) implement the `ClassLikeNode` interface, because an anonymous class is not a statement; it declares `$name` (null for the anonymous one) and `$members`. The five kinds written with parameters and a body implement `FunctionLikeNode` for the same reason, declaring `$parameters` and `$returnType`, both null where a property hook has none. `Scope` returns them intersected with `Node`, so a result is still a node to search in.
- A `VariableNode` is a variable being used, so a rule about variables can take every one of them: the name of a static property is written the way a variable is (`A::$b`, `A::$$b`, `A::${expr}`) but is a name, and `StaticPropertyFetchNode` holds the `dollar`, `openBrace`, `name` and `closeBrace` of that writing in slots of its own, `$plainName` giving the name without the dollar. The `$b` of `A::$$b` is a `VariableNode` again, because that one is read. A variable that is being declared rather than used is a `VariableNode` too, in the `variable` slot of `ParameterNode`, `CatchNode`, `ClosureUseNode` or `StaticVariableNode`. So is the bare name of `"${name}"`, whose token carries no dollar, which is why the name of a variable is read as `$plainName` and not from the text of its token.
- An expression written with an operator implements `OperatorNode` and says through `getPrecedence()` how tightly it binds and which side it leans to, in the numbers of the precedence declarations of the grammar. One written with no left operand, whose right one reaches as far as the code lets it, implements `RightExtendingNode`, an `OperatorNode` itself: an arrow function, throw, print, yield, yield from and include capture nothing before themselves, so where nothing follows them they stand bare however loosely they bind. `ParenthesizedNode::isRedundant()` reads that from both sides of a pair of parentheses and answers whether they may go, and no where it is not certain. What follows them is not only what stands beside them: it is the next token of the nearest ancestor they do not end, so `$a + (yield $b) + 1` keeps them although the yield ends the sum it stands in. And what would take it is not only the expression in them but whatever operator ends it: a prefix operator (`!`, `-`, `@`, a cast) captures nothing before itself either and takes what binds at least as tightly as itself, so `(bool) (!$a)` loses them and `(!$a) instanceof B` keeps them, and `(@include $f) !== false` keeps them for the include inside. Precedence is not all it asks: a pipe takes an arrow function in parentheses only, and `::` takes the name of a class on its left, so the parentheses of `(FOO)::class`, `(FOO)::BAR`, `(FOO)::m()` and `(FOO)::$p` are what makes the name an expression, `FOO::class` being the name `FOO` itself and `(FOO)::class` the class of what the constant holds; `true` and `null` are written as names too, while anything else there is an expression either way, and `->` and `[]` take one whatever stands before them.
- `ExpressionNode::toValue()` gives the value an expression is written as, a scalar, null, true, false or an array of them, and throws where it is written as none, which `hasValue()` asks beforehand. A name is not a value: what it stands for is a matter of what the code around it defines.
- The layout role of a slot (`LayoutData`, generated from `grammar/nodes.php`: the convention by the name of the slot, `layout` where the schema says otherwise) says what the slot is to the indentation of the lines the node spreads over, which is what a tool laying out code by the tree alone counts from. The convention goes by the name of the slot alone (`close*` and `endKeyword` are `Closes`; `open*`, `*Keyword`, `modifiers`, `attributes` and `semicolon` are `Anchor`; `body` is `Body`; the rest is `Content`), so renaming a slot changes its role unless the schema pins it. The table is keyed by a class and a slot, so a role belonging to one operator alone is not in it: `Indentation::findRole()` gives the `operator` and the `right` of a `BinaryOpNode` of `|>` the role of a link, a pipeline being a chain of calls and laid out as one.

## Analyses

An analysis is information derived from a file: `NameResolver` (namespace, imports, resolution of class, function and constant names with the runtime fallback of unqualified functions and constants to the global namespace, `isGlobalFunctionCall()`, the name a declaration introduces and the declaration of a name (`getDeclaredName()`, and `findDeclaration()`, which looks among the symbols of one `SymbolKind`, PHP keeping a class, a function and a constant of one name apart, in the declarations collected once for the file, so it costs a lookup and gives the first declaration of a name the file repeats), and the way back: `getShortName()` gives the shortest way to write a fully qualified name where a node stands, through an alias, a prefix import or the namespace, and `isAliasFree()` says whether a name is still free there, which is what adding an import asks) and `Scope` (enclosing function-like construct and class, availability of `$this`, captured variables).

An analysis that derives something from the whole file takes the `FileNode` in its constructor and keeps what it has read, `NameResolver` among them: it reads the tree as it was, so a caller that mutates the tree builds the analysis anew, which `FileNode::$revision` tells it to do. `Scope` keeps nothing and takes nothing, every question being answered by walking the parents of the node it is given, so it outlives any mutation.

Imports belong to the namespace block they are written in, a declaration to the namespace itself, so a second `namespace A {}` block of the same file sees what the first one declared and none of what it imported; a declaration inside a condition or a function body counts too. An unqualified function or constant declared in another file is invisible to the file, so the resolver takes such a name as global unless the `NamespacedSymbols` given to the constructor list it; whether the list says it is complete decides only how certain that answer is. `getUnqualifiedResolution()` tells such a name taken as global (`UnqualifiedResolution::Uncertain`) from one known to be (`Global`) and from one reaching a symbol of a namespace (`Namespaced`), the question a tool rewriting a call of a global function asks before calling the rewrite safe; it takes an unqualified name only, since no other name falls back, and `Global` says that the name reaches the global namespace, not that it reaches the symbol it spells, which an import may rename. `getShortName()` writes a function or a constant bare only where the bare name reaches it for certain.

A node from another tree is refused, not answered in the global namespace, because a valid answer to a question nobody asked is worse than an exception, and so is a name that refers to no symbol (`NameNode::isReference()`): `int` in a type, the name a `use` introduces; self, static and parent come back as they are. `resolveClass()`, `resolveFunction()` and `resolveConstant()` take `$at` for the node the name is to be read at, which is what a name lifted out of the file into a copy needs, as `getShortName()` and `isAliasFree()` do.

## Parents, mutation and the index

- A node or token belongs to exactly one tree: `$parent` is set by the parser and by the mutation API, and inserting a node that already has a parent throws. Two values may have one. A node standing inside the child the write releases (`$paren->replaceWith($paren->expression)`, `$assign->expression = $binary->right`), which is how an operand is taken up in place of what holds it. And a node standing in a subtree whose root is not a `FileNode`, where no index can come apart over it, so a codemod replaces a call and then takes out of it what the replacement needs, and a fragment gives up a part of itself. What is left of either still points at the value, so it is waste and not material, and whoever wants it whole clones it before the write; a value taken this way carries the trivia of the place it came from, the way a clone does, and `setEdgeTrivia([], [])` clears them. A child of the node doing the write is taken from nowhere, because taking it from itself would put it in twice. `clone` gives a deep copy without a parent, over the slots and the items of the lists, never over a property computed from the tokens, because such a property may throw, as the `$value` of a heredoc that interpolates does.
- A slot is a public hooked property, written by assignment (`$node->condition = $expression`, `replaceChild()`, or `setSlot()` given the name of the slot): the set hook the generator writes (`set => $this->prepareSlot(__PROPERTY__, $value)`) calls `Node::prepareSlot()`, which refuses a value that has a parent, adopts it, releases the current one and reports `structureChanged()`, and returns the value the hook writes; a detached node only sets the parents, having no file to report to. The type of the property is what refuses a value that does not fit, before the hook runs, and `setSlot()` refuses a name that is no slot of the node before that. The rest of the mechanics live once in `Node`, over the `Slots` constant every node class carries (its slots in source order): `getChildren()`, `getFirstToken()`, `findSlotOf()` and `replaceChild()`. The hooks run in the constructor too, so a node adopts its children as it is built; the handwritten lists, which have no `Slots` and read their items themselves, adopt theirs in the constructor the same way, so a node is never built and attached in two steps.
- Everything a write refuses, it refuses before it moves anything: `Node::checkValue()` refuses a value that holds the node written into, which would make a cycle, and one standing where the write may not take it from, and moves nothing, and `Node::prepareValue()` checks a value and then frees it, for every write, the lists and `ModifiersNode` among them. A write of several values, an item with its separator, checks all of them before it frees any, and refuses values that overlap, a separator taken out of the item it is to separate, which would stand in two lists at once. So a refused write leaves every tree it was given exactly as it stood, trivia and all, the fragment a value came from included, and `replaceWith()` moves the trivia of the old node only after the parent has taken the new one.
- Lists mutate through `append()`, `insert()`, `removeItem()`, `replaceChild()` (`removeItem()` and `ModifiersNode::removeToken()` are named apart from `Node::remove()`, which removes the node itself, because PHP forbids an incompatible signature in a child class); `SeparatedNodeList::insert()` derives a missing separator from the existing ones (or `", "` in a one-line list) and gives the item the indentation of its neighbor in a multi-line list; a separator carrying a comment models nothing, the comment being content that a copy would duplicate, so the next separator stands in for it, `removeItem()` takes the separator after the item, or before the last one (`findSeparatorOf()`), and the item goes with all its trivia, comments included, tidying no line; that is what `Node::remove()` adds. `NodeList::insert()` models the neighbor too, there being no separator between statements to carry the line ending: an item that carries no trivia of its own takes the indentation of its neighbor and ends its line the same way, as long as the list stands in a file and the item does not end its line inside its own text, as a close tag and inline HTML do. The constructors of the lists, internal and fed by the parser with fresh nodes, adopt their children one by one and promise none of this.
- `Node::remove()` removes a list item together with the separator that goes with it: a node alone on its lines takes the lines with it, otherwise the whitespace around stays, the gap the separator opened goes with it and whatever is left dangling before a line ending is trimmed; its comments, those on its edges included, each with the line ending after it and the whitespace indenting it, go to the next token, the previous token (the next one where there is none), or away, as the `CommentPolicy` says. The default keeps every comment, so a doc comment of a removed declaration becomes that of whatever follows it, and a caller to whom that is wrong refuses such a node or drops the comment knowingly. `Node::replaceWith()` keeps the trivia around the old node around the new one by joining them with the new node's own edge trivia; a replacement cloned from nearby source still carries its original leading trivia, so that an `OpenTag` gets doubled, which is why such a copy is taken with `Node::withoutEdgeTrivia()` and not with `clone`. A replacement may also come to stand right against a token it would be read together with, `'a'.` against `119`, `return` against `FOO`, `-` against `-$a`; `replaceWith()` asks the lexer about the two seams (`Lexer::canAdjoin()`, which whoever takes whitespace away from between two tokens asks as well) and puts a space where the pair reads as something else without one and as itself with one, in a subtree without a file too. Writing a slot by assignment does not ask. `ExpressionNode::replaceWithExpression()` is the same for an expression that may bind looser than the place it goes to: it puts the expression in parentheses and takes them away again where `ParenthesizedNode::isRedundant()` calls them needless, so the question of precedence has one answer.
- Where a property is written and where a method is, is decided by how many values the write takes. A property is read whenever the answer is derived from the tokens (`value`, `base`, `quote`, `label`, `indentation`, `kind`, `parts`, `role`, `text`), and it is written when the write takes exactly one value and has one consequence: the slot of a node, and `NameNode::$text`, whose hook tokenizes the name anew. A method writes when the write takes more than one value or when two things must change together, because two properties would mean that writing one reads the other and the caller has to think about the order: `StringNode::setValue($value, ?$quote)` is that case, the delimiter deciding how the value is written. The text and the trivia of a token are methods for a third reason: `?->` cannot stand on the left of an assignment, so `$node->getFirstToken()?->setText('x')` has no property form. `Token::setText()`, `setLeadingTrivia()` and `setTrailingTrivia()` do for a token what the hook of a slot does for a node, and `Node::setEdgeTrivia()` writes the trivia on the outer edges of a node, where the first or the last token may be missing. The lexer and the parser go through the same setters on tokens that are not in a file yet, where there is no index to tell.
- What neither a hook nor a setter covers the language guards instead: the text and the trivia of a token are `private(set)`, the items of a list are `protected(set)`, and `parent` is `private(set)`, written by `attachTo()`, which is why no PHPStan rule watches the tree. A `private(set)` array takes no indirect change from outside, so `end($token->trailingTrivia)` needs a copy.
- The setters are what keeps the index right: `FileNode` owns the `TokenIndex` (order, previous/next token, offset, line, column, visual column) built lazily and kept up to date rather than rebuilt. A structural change reports the children it adopted and released and `structureChanged()`, and the index moves their tokens at its next query, when the tree has its new shape whatever the order of the writes, so a run of writes that only adopt costs one move, while a write releasing a child reads the order to find its tokens and so makes the pending move first; a token setter reports `tokenChanged()` with the line endings the token gained or lost, and the lines before the token stay as they are; only offsets and columns are recomputed from scratch. The numbering and the lines of the tokens after a change are brought up to date lazily, as far as the queries reach, so the cost of a change of text or trivia followed by a query nearby is proportional to the distance, not to the file; a structural change adds the move, which shifts the tokens after it and so costs in proportion to the file. A tree changed behind the back of the index is a `LogicException` once the index reads its order again, not a slow path, and so is a subtree entering a file with a child a write took out of it, which would otherwise stand in the order twice. Every mutation increments `FileNode::$revision`, which is how a caller detects one. A token carries its index and the index that numbered it (`Token::$index`, `Token::$indexedBy`, both `@internal`), which is how navigation finds the file without walking the parents; the shortcut is verified against the index before use, so a token moved to another tree falls back to the parents. Navigation from a detached subtree returns `null`. `TokenIndex::getOffsetRange()` gives the byte offsets of a node or token in the current text, and `findNode()` the outermost node of a class standing exactly at given offsets, which is how a position another tool computed over the same text (php-parser, an editor) is brought to the tree; `tests/PhpSyntax/Parser/php-parser-parity.phpt` holds that every expression of the tree stands where php-parser has one and the other way round, apart from a destructuring pattern (a `ListNode`, no expression), the parentheses (php-parser has none) and what is written inside a string (each models it in its own way).
- `Token::$originalLine` and `$originalOffset` never change and are the source of positions in reports; `getLine()` and `getColumn()` follow mutations.
- A node reads its own text and its own edges: `$text` is what is written between its first and its last token, the trivia on the outer edges left out, which is what a report prints, while printing the node writes those edges too, as the round trip needs; `$leadingTrivia` and `$trailingTrivia` are those edges, and `setEdgeTrivia()` writes them. `getTokens()` gives the tokens of the whole subtree in source order.
- A single trivia (typically a comment) is removed by `Token::removeTrivia()`, which tidies the whitespace around it: one alone on its line takes the line with it, an inline one takes an adjacent space; `Token::replaceTrivia()` swaps one in place. A node does the same for a trivia of any of its tokens, or of the one before it where a doc comment of the node may stand (`Node::removeTrivia()`, `Node::replaceTrivia()`), which is what closes the way from a comment found on a node to the mutation removing it. A doc comment is read with `Node::getDocComment()` (above the node, or after the previous token) and written back with `Node::replaceDocComment()` or dropped with `Node::removeDocComment()`; what a doc comment says is for the caller to parse, the tree only carries its text. A `Trivia` is an immutable value, so the same instance may sit on several tokens, and a mutation naming one finds it among the trivia by identity.
- Comment queries for whoever must not destroy a comment: `Token::hasComment()` (in the trivia of the token), `Token::hasCommentUpTo()` (anywhere between the texts of two tokens) and `Node::hasComment()` (inside the node, its outer edges excluded); `Token::getComments()` and `Node::getComments()` give what those count, and a `Trivia` says of itself whether it `isDocComment()`, `isLineComment()` or `isMultiLine()` and hands over its text without the delimiters as `getCommentText()`. The queries of a node walk its own tokens and need no index, so a subtree taken out of the tree answers as it did inside it.
- `Node::matches()` compares two nodes by their token texts (`getTokenTexts()`, which is also what a tool keys a map by where the layout must not count; the size of code is measured on `$text`, which keeps it), `ExpressionNode::isRepeatableRead()` tells whether reading an expression again is free of side effects; together they answer "does this assignment repeat its target". That answer is syntactic: a magic getter or a hook behind a fetch, an `ArrayAccess` behind an offset and a `__toString()` behind an interpolated string are out of its sight, and whoever cannot assume that much needs the types, which a syntax tree does not have.
- `ExpressionNode::getAccessKind()` tells how the parent reaches into the expression, as an `AccessKind` (`Member` for `->` and `[]`, `Call` for `(...)`, `ClassName` for `::`) and null where it does not reach in at all, which `isDereferenced()` is the same question asked without the kind; `isDereferenceable()` answers the other way round whether what is written after the expression may reach into it with no parentheses around it, which differs by what that is and so takes the same enum, `canNameClass()` whether it may stand where a class is named, and `isWritable()` whether it may stand where a place is assigned to, which a `?->` anywhere in the chain the write reaches through rules out, a call in the chain included, and so does a chain starting at a value of its own, a literal, a constant, `new` or `clone`, the way PHP refuses both; `ParenthesizedNode::isRedundant()` asks all of them along with the precedence of both sides.
- Horizontal whitespace between two tokens on a line is the trailing trivia of the first one, never the leading trivia of the second (whoever joins two lines writes the space there, or the next reader of the gap sees none), and it is read and written through `Token::getTrailingSpace()` and `setTrailingSpace()`, which return or refuse `null` when a line ending, a comment or string content is in the way, or when the first token ends its line by its own text (a close tag, a heredoc start); `Token::is()` given a text never matches the content of a string, only operators and punctuation. `Token::getLineWidth()` measures the line of a token visually, a tab moving to the next stop of the style wherever on the line it stands, which is the same counting `getVisualColumn()` does and what the reader sees. `Token::removeTrailingWhitespace()` takes away the whitespace the trailing trivia end with, which in the middle of a line is the space before the next token, so the two come to stand together and `Lexer::canAdjoin()` is not asked; it also trims the end of a `//` or `#` comment, because the tokenizer counts the spaces before the line break as part of the comment text; a caller therefore changes a comment by it.
- A mutation keeps the trivia canonical: the line ending that ends the line of a token belongs to that token's trailing trivia, never to the leading trivia of the next one. A misplaced one makes `getTrailingSpace()` blind to the line break; `ensureLeadingNewline()` and `setBlankLinesBefore()` place it correctly, so build on them.
- The whitespace conventions of a file are a `Style`: the indentation unit, the line ending (`Style::detectEol()` reads the prevailing one) and the width of a tab, which is what visual columns and line widths count with.
- Indentation is changed through `Indentation` (`set()` a line and the comments above it, `normalize()` into the characters of the style) and `Token::getLineIndentation()`; `Token::setIndentation()` alone moves one line and leaves the rest of the statement where it was. `Indentation::findOwner()` and `findRole()` tell which construct a line-opening token continues and in what role, and `Indentation::infer()` gives the indentation such a line conventionally has, counted from the line its construct begins on. `Indentation::opensLine()` says whether the line ending above a token is trivia, which is the only case its indentation is whitespace to write: `Token::startsLine()` also answers yes after inline HTML, a heredoc body or a close tag, and there the leading whitespace is text. `Indentation::shift()` moves every line a node opens by a level, and with them the body and the closing delimiter of a heredoc, which keeps the value it stands for; inline HTML and the content of a string are text of their own and stay.
- `Node::getChildren()` is the children in source order, empty slots left out, and the only way to the children: a node is not iterable, so that there is one way and it is an array, which the printer, the index and the traverser read directly. `Node::find()` takes a class and a predicate that narrows it, and gives the descendants of that class the predicate accepts as a snapshot safe to iterate while mutating, `Node::findFirst()` stops at the first one; the class may be an interface node classes implement, as it may for `findAncestor()`, and the predicate gets the node typed, so a slot of it is reached without an instanceof. The `Traverser` walks in pre-order with `traverse($root, $enter, $leave)`, a callback steering it with `DontTraverseChildren` or `StopTraversal`, and it leaves every node it entered, so a callback keeping a state of its own stays right; it does not descend into a replaced node, skips siblings detached meanwhile and leaves inserted ones for the next walk. A node the walk hands over may therefore be one a callback has already taken out of the tree, which its `parent` says (null for anything but the root), and whoever passes the nodes on to somebody else filters by that, because `replaceWith()` and `remove()` throw on a node outside the tree, and a write into one changes what no file prints.
