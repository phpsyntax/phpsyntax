# PhpSyntax internals

How the syntax layer works: the facts an agent or a contributor needs before touching the lexer, the grammar, the nodes or the mutation API.

The library has no dependencies and never imports Nette, php-parser or anything from `vendor/`: `composer.json` requires PHP and `ext-tokenizer` and nothing else, and what the tests and the tools need is `require-dev`. Everything under `PhpSyntax` is public API but for what says `@internal`, so a tool built on the library may reach for any of it. The nodes, the lists and the interfaces of the nodes are the library's own: a class extending one or implementing such an interface elsewhere is not supported, so the protected members of the nodes, the machinery of the writes (`prepareSlot()`, `adopt()`...), and the generated `TokenData` belong to the library and change with it, and an interface of the nodes may gain a member. What such a tool uses stays public, and a helper only the classes of the library share is `@internal` with that reason (`TokenIndex::countLineEndings()`), which is how the surface is decided for a new method too.

## Tokens and trivia

The lexer (`PhpSyntax\Lexer`) turns `PhpToken::tokenize()` output into significant tokens; whitespace, comments and open tags become `Trivia` attached to tokens:

- **Trailing trivia** of a token is everything after it up to and including the first end of line. **Leading trivia** of the next token is everything else (blank lines, indentation, comments on their own lines, doc comments). Whitespace is split into `Whitespace` runs and single `LineEnding` pieces (`"\n"`, `"\r\n"` or a lone `"\r"`). The line ending of the line above belongs to the token that ends it, so an `LineEnding` among leading trivia is a blank line or the end of a comment's own line: an indented token below one blank line leads with `[LineEnding, Whitespace]`, one directly below the previous line with `[Whitespace]` alone.
- Exceptions: an `OpenTag` trivia (`<?php` with its mandatory whitespace) is always leading trivia of the following token, and everything after it too; the final `EndOfFile` token has only leading trivia, never trailing; a token whose text ends with a newline (`CloseTag`, a heredoc start) ends its line the same way an `LineEnding` does.
- `<?php` is not a token. `?>` is a token of kind `CloseTag` that keeps the newline PHP swallows after it, and the parser sees it as `;`; after a terminated statement it forms an `EmptyStatementNode`. `<?=` is a token of kind `OpenTagWithEcho` seen as `echo`. A `semicolon` slot therefore holds either `;` or `?>`.
- Whitespace that PHP counts as part of a token stays in its text: inline HTML, `T_ENCAPSED_AND_WHITESPACE`, heredoc delimiters (the closing one keeps its indentation), casts like `( int )`.
- Trivia inside string interpolation (`"{$a /* c */ }"`) carry `inInterpolation = true`; the token helpers refuse to change them because inside a string whitespace can change what is read: `"${a}"` interpolates `$a`, `"${a }"` the variable the constant `a` names.
- A BOM or a hashbang line is inline HTML, as PHP sees it; `InlineHtmlNode::isPreamble()` tells whether that is all the text is, which is what makes a file pure PHP. A single-line comment never contains its newline, but it does contain trailing spaces before it.
- A kind is the id `PhpToken` gives the token: the kinds are constants of `Token`, from the generated trait `TokenData`, a kind of the grammar being its `T_*` constant, so the lexer takes the id as it is. A token of a single character has the ordinal of that character as its kind (`ord(';')`), not a named constant. A keyword is named by the word itself (`Token::If`), except `ClassKeyword`, `class` being reserved for `::class`, and `NamespaceKeyword`, which PHP reserves from 8.6. A kind PHP has no token for is 0 or negative (`EndOfFile`, `HaltCompilerData`), and so is a token of a newer PHP on a runtime that lacks it (`Pipe` and `VoidCast` before 8.5); no constant is defined at runtime (php-parser does that), because a library must not have that global side effect. The values differ between PHP versions, so a kind is compared, never stored. A `Trivia` is a `PhpToken` too, one PHP ignores, and its kinds are the constants of `Trivia`: `Whitespace`, `Comment`, `DocComment` and `OpenTag` are the ids of the tokenizer, `LineEnding` a negative one of its own, since the lexer splits a line ending out of `T_WHITESPACE`. The lexer goes over the output of `PhpToken::tokenize()` once and makes a `Token` only of a significant piece. Syntax of PHP 8.5 on an older runtime is emulated by rewriting that output before the folding (`PhpSyntax\Emulators`); a token an emulator makes carries its negative kind. The emulators are `@internal`: one of another hand would have to keep the raw tokens, their ids and positions and the sparse array they come in, and the helpers that read a single token (`Lexer::readToken()` behind `Token::fromText()` and `canAdjoin()`) run the lexer of the library, not the one a file was read with. Emulation makes the one syntax of the grammar readable on an older runtime; it does not choose a version of PHP to parse.

## Round trip

`Printer::print(new Parser()->parse($code)) === $code` byte for byte for any input PHP accepts, including BOM, hashbang, CR/CRLF, close tags, inline HTML and `__halt_compiler()` data. It is the invariant every change to the lexer, the grammar, the nodes or the printer must keep; the tests run it over the committed corpus (`tests/corpus/`) and, with `PHPSYNTAX_CORPUS` set, over an external tree. The printer is a concatenation and has no logic of its own, so what a tool changes in the trivia and the nodes is exactly what the text gets.

## Parser and generated files

The parser is an LALR(1) driver over tables generated by phpyacc from `grammar/php.y`, a fork of the nikic/php-parser grammar with the PHP 7 branch and the error-recovery productions removed. Productions are never changed, only their semantic actions. `composer compile-grammar` regenerates `src/ParserData.php`, `src/TokenData.php` and `src/LayoutData.php` from `grammar/php.y` and `grammar/nodes.php`, and in every node class the `Slots` constant, the slot properties and the constructor; the output is committed, so a change to the schema and a rebuild belong to the same commit. A file generated whole says so with `@generated` in its header.

A node class is a handwritten file whose two generated members the generator replaces in place: it finds the `Slots` line and the constructor (from `public function __construct(` to the first `}` on a line of its own) by the shape it writes them in, and fails when it finds either zero or several times, so a class never falls behind the schema in silence. The schema (`grammar/nodes.php`) holds only the slots of a class and the layout roles that differ from the convention; the description, the parent, the interfaces and the methods belong to the class. The generator is deliberately simple, because the schema changes once a year with a PHP version and a person is at the keyboard: a missing class is written as a skeleton to complete, a missing import is reported and added by hand, a file the schema does not know is reported and never deleted. The procedure for a new PHP version:

1. Add the tokens and productions to `grammar/php.y` with their actions, and the slots of new or changed nodes to `grammar/nodes.php`.
2. `composer compile-grammar`; fix what it reports: complete the skeleton of a new class (docblock, parent, interfaces, methods), add the imports it names, delete a class that is gone; the code style of `dresscode.neon` always runs over the output before it is committed, so the generator is not required to reproduce the committed files, and a bare rebuild differs from them.
3. `composer tester` with new dump fixtures in `tests/PhpSyntax/Parser/dump/`, then `composer phpstan`.

- The token declarations are in the header of `php.y`, so there is no separate token grammar; `TokenData` is generated from that header, and the `TokenToSymbol` table of `ParserData` names the kinds, phpyacc numbering the tokens its own way. phpyacc must report exactly the two shift/reduce conflicts of the dangling else that `%expect` declares, and a change in that number means the grammar was altered, not just its actions. `ParserData.php` is analysed by PHPStan like the rest, with one ignore for the node constructors its actions call: an action builds a list from the item its production has, while the slot is typed by every kind that may stand in it. What its actions put on the untyped value stack is guarded by the grammar, the coverage check and the round trip instead.
- Every grammar alternative with two or more symbols must have an action that uses every symbol, otherwise tokens would drop out of the tree; the build fails on such an alternative. A single symbol passes through, an empty alternative yields `null`.
- Actions may put plain arrays of slot values on the value stack (tails of alternative syntax, optional pairs such as `: type`); they are spread into the node constructor and never leave the parser.
- After parsing, statements following `namespace A;` are nested into that `NamespaceNode`, so every namespace has its statements as children; only `__halt_compiler()` stays outside.
- The data after `__halt_compiler();` is a token in `HaltCompilerNode::$data`.
- A piece of code that is not a whole file is read by `Builder::fragment()` into a node of the class given, `Builder::expression()`, `statement()`, `type()` and `name()` being its typed shortcuts, while `Parser` reads a whole file with `parse()` alone. The engine is the `@internal` `Parser::parseFragment()`, which parses the piece inside the code such a node stands in: the wrappers name a kind each (`ExpressionNode`, `StatementNode`, `MemberNode`, `ParameterNode`, `ArgumentNode`, `ArrayItemNode`, `UseItemNode`...), and a class deriving from one of them is parsed in the same wrapper. The node comes back detached, with empty trivia on its edges and without original positions, and what leaves something over is refused: the node has to reach from the first token after the prefix to the last one before the suffix, which is how `$a, $b` given as one parameter is caught. This is how a new node is built: a node constructor is `@internal`, its parameters following the slots of a grammar the next version of PHP may extend.
- A name, an identifier and a string literal are also made from their text or value (`NameNode::fromText()`, `IdentifierNode::fromText()`, `StringNode::fromValue()`), and a `Token` and a `Trivia` from their text, `Token::fromText()` running the lexer so that the kind is the one PHP gives the text and `Trivia::fromText()` telling whitespace, a line ending, a comment, a doc comment and an open tag apart, or constructed directly with a kind.
- A `ParseException` says where in the source the error is with `$sourceLine`, `$sourceColumn` and `$sourceOffset`, told apart from the `getLine()` and `getFile()` of the exception itself. An error of a fragment is told in its terms: the position is counted in the fragment, and a token of the wrapper never reaches the message, the error beyond the fragment being `Unexpected end of the fragment`. An unterminated string, heredoc or shell command is refused by the lexer where it starts, the parser would only reach the end of the file.

## Exception messages

An exception is read by the author of a tool who parsed a fragment or wrote into a tree, with the stack trace beside it. It is one sentence, capitalized, ending with a period, that says what the call met, and what was expected where that is not evident; the refusing API is named only where the trace does not show it, as in the index, which finds a broken tree later than the write that broke it. The subject is the thing refused, `The node`, `The trivia`, a token by its text (``Token `$x` ``). Everything in the message that is code stands in backticks, as in Markdown: a value the caller passed, a token by its text, a slot, a class, a method, an operator, a name; a word about code stays prose (`The node`, `The trivia`, `a list`). Code that can itself hold a backtick (the text of a token, a value from the caller, source text) is written by `Helpers::formatCode()` as a code span in a run of backticks longer than any inside it, padded with a space where it starts or ends with a backtick.

A `ParseException` of the grammar follows the syntax errors of PHP, `Unexpected <what>, expecting <list>` and `Unterminated <what>`, with no period, because a caller appends the position. The token found and the tokens expected by their spelling stand in backticks (``Unexpected `;`, expecting an identifier or `{` ``), the tokens named by kind stay words with their article (`an identifier`, `a variable`, `end of file`), and none is named by the lexer constant (`Parser::TokenNames`). The byte of an unexpected character is a number, not code, and stands bare (`Unexpected character 0x0A`). An invariant of the parser itself is a `LogicException` for the maintainer and takes the form alone.

## Tree

- Every node class ends with `Node`; slots are named by role (`ifKeyword`, `openParen`, `semicolon`, `condition`, `body`), paired delimiters are always `open*`/`close*`, lists are plural or bear the keyword that introduces them (`extends`, `implements`). Every token of the source has a slot or a place in a list, so the order and number of children are not part of the API, only the slot names. Whoever names a slot instead of reaching for it writes the name as a string (`'openParen'`), and the `Slots` constant of the class is what such a name is checked against, which is how a table of them is verified at startup instead of falling silent after a slot is renamed.
- A node is named by the word PHP itself writes, keyword or function (`IfNode`, `ThrowNode`, `ShellExecNode`, `HaltCompilerNode`), and by a noun where PHP writes no such word (`ArrayAccessNode`, `PropertyFetchNode`, `CombinedAssignmentNode`, `TernaryNode`); a bare verb is not a node name, and where the manual has a term for the construct, that term wins over the one other languages use, which is why a compound assignment is a combined one here.
- A slot says what stands in it, not what the reader could guess from the class. The target of a write is `target` and not `variable`, because it is any writable expression and `isWritable()` is the question asked of it; what a `switch` and a `match` compare against is `subject` and not `condition`, because it is not evaluated for truth; a `case` carries `value` and a `match` arm `values` for the same reason. Names of the API are written in full, a local variable may be abbreviated; the abbreviations left in the API are `paren` in `openParen`/`closeParen`, the delimiter having no one-word English name, and `Op` in `BinaryOpNode` and its kin.
- Lists: a `NodeList<T>` is either a `PlainNodeList<T>` (statements, members, attribute groups) or a `SeparatedNodeList<T>` (parameters, arguments, items, imports) with separator tokens between items and an optional trailing separator; `SkippedArrayItemNode` stands for nothing between two commas of a destructuring list. The abstract class is the type a tool asks for where either will do, while a slot names the one it holds, so that a list with commas never stands where statements do. `ModifiersNode` holds modifier tokens in source order. A list is read as a collection, iterated, counted and indexed directly (`foreach ($call->arguments->items as $argument)`, `$call->arguments->items[0]`), and `getItems()` gives the same items as an array (`getTokens()` in `ModifiersNode`), so the slot `items` a node holds a list in is never followed by a second `items`; the iteration is a snapshot, safe while the list is being mutated, and an index outside the list is an `OutOfRangeException`, while `$list[$i] ?? null` asks. A read-only helper over any list writes `@param NodeList<covariant Node>`, the type parameter being invariant. `ModifiersNode::$visibility` is the effective visibility, `Public` where none is written (`var` is public too) and `$writeVisibility` the effective one for writing, that of `public(set)` and its kin, `Protected` for a public `readonly` (PHP 8.4 writes such a property as `protected(set)`), or else the `$visibility`, read from the modifiers alone as `$readonly` is, so the readonly of a class is not seen there; `$static`, `$abstract`, `$final` and `$readonly` tell whether that keyword is written; whether a visibility is written is asked of `ModifiersNode::getVisibilityToken()`, and whether a parameter declares a property, which `readonly` or `private(set)` alone does without any visibility written, of `ParameterNode::$promoted`. Which argument of a call a parameter gets is `ArgumentListNode::findArgument()`: the one written with its name first, then the one at its position, a `?` placeholder holding a place without being an argument, and no position after an unpacked argument has an answer.
- `Node::getFirstToken()` and `getLastToken()` are null for a node without tokens, an empty list, an empty `ModifiersNode` or a `SkippedArrayItemNode`. A class that has a required slot holding a token, or a node that always has one, narrows both to `Token` by a `@method` in its docblock, which no native type can do for an inherited method: the expressions, the statements, the trait adaptations, the members, the named and the nullable type and the nodes that stand in their slots (`NameNode`, `ArgumentNode`, `FileNode`...), which `tests/PhpSyntax/Nodes/first-last-token.phpt` checks against the slots. `PropertyNode`, `UnionTypeNode` and `IntersectionTypeNode` do not, every token of theirs standing in a list a mutation may empty, and so neither do `MemberNode` and `TypeNode` above them. A token is its own first and last token, so a `Node|Token` is asked directly.
- The body of a control structure is a `StatementNode`, not necessarily a block; `else if` is an `ElseNode` whose body is an `IfNode`. The alternative syntax uses the same classes with `colon`, `statements`, `endKeyword` and `semicolon` slots instead of `body`. An import is one `UseNode` however it is written, the group form filling the `prefix`, `openBrace` and `closeBrace` slots the plain one leaves empty (`isGroup()`), and `UseItemNode::$fullName` is the name an item imports, the prefix of the group included. What an item imports is said by the statement it stands in, so an item is never moved from one statement to another but written anew by `UseNode::addImport()`, the way the statement writes its items.
- Destructuring is a `DestructuringNode` whichever of its two spellings is used, the `listKeyword` being null for `[...]`, and so is a destructuring nested in one, however deep and whichever spelling either of them uses. A short array is built as an `ArrayNode` and turned into a `DestructuringNode` where it stands as a target: the left of an assignment and the value of a `foreach`. An `ArrayNode` is therefore an array literal and never a destructuring. A `DestructuringNode` is no expression, having no value of its own to answer for: it stands only where a target is written, which is what the slots `AssignmentNode::$target`, `ForeachNode::$value` and `ArrayItemNode::$value` say by holding `ExpressionNode|DestructuringNode`, and a caller that asks a question of expressions there narrows first.
- Every scalar literal is a `ScalarNode`, whatever it is written with, so a question about literals is one `instanceof` and not a list of nine classes; `ExpressionNode::isRepeatableRead()` is one that asks it. Scalars keep their raw text (`IntegerNode::$token->text` is `0x1F`) and give the value it stands for by `toValue()`, with `$base` beside it for an integer and `$quote` for a string, and an integer literal beyond the integer range is a `FloatNode` whatever its base, because PHP reads it as a float, so not every integer written is an `IntegerNode`; `StringNode::setValue($value, ?$quote)` changes how a string is written without changing what it is; a heredoc answers `hasInterpolation()` before its `toValue()` can be asked, and that value is the body outdented first and read for escapes afterwards, the indentation being physical while what `\n` makes is no line of the source to outdent, and an offset written without quotes inside an interpolated string is an `UnquotedStringNode`, so a string always has a delimiter to write a value with. `StringNode::fromValue()` goes the other way and writes a value as a literal. `true`, `false` and `null` are literals too (`BooleanNode`, `NullNode`), not constant fetches, although the grammar reads them as names: they keep the letter case and the leading backslash they are written with, and a qualified or relative name of the same spelling (`A\true`) stays a `ConstantFetchNode`, because that is the constant PHP would look up.
- Operators are one `BinaryOpNode`, `UnaryOpNode`, `PrefixOpNode`, `PostfixOpNode`, `CombinedAssignmentNode` with the operator token, or a `CastNode` with its `operator`, plain `=` being an `AssignmentNode` of its own, because the grammar takes a destructuring on the left of that one alone, and `++`/`--` are a `PrefixOpNode` or a `PostfixOpNode` rather than a unary operation, because the grammar takes a variable for them and any expression for `-` and `!`.
- Names are one `NameNode` with a token of any kind, including keywords the grammar accepts as names, and its `$text` is what is written there (writing it replaces the token with the kind the new name needs), `$parts`, `$shortName` and `$form` take it apart and `$symbolKind` tells from its place in the tree whether it stands for a class, a function or a constant, classes and namespaces being one table of names in PHP, while `isDeclaration()` tells a name a use or namespace statement introduces from one that refers to something, and `isReference()` whether the name refers to a symbol at all: not a declaration, not self, static or parent, and not a builtin type where a type is written, which is what the resolver refuses. `equals()` compares the writing with a string, a constant exactly and anything else regardless of letter case, the leading backslash being part of the writing; whether two names mean one symbol is for `NameResolver`. What is written as an identifier instead (the name a declaration introduces, a member, a label, an alias, the name of a named argument) is an `IdentifierNode`, one token whose `$text` takes an identifier and nothing else, and whose `equals()` tells from its place whether PHP reads it regardless of letter case, a method yes and a property no. Either reads its text as `->text`, and the slot holding it is named by its role (`name`, `class`, `extends`, `method`, `label`). What a name or an identifier answers from its place, the kind of symbol, the letter case `equals()` ignores, the kind and the group prefix an import item has, a node taken out of the tree no longer knows (a detached name is a class), so a tool reads it before the write that moves the node.
- Class-like declarations (`ClassNode`, `InterfaceNode`, `TraitNode`, `EnumNode`, `AnonymousClassNode`) implement the `ClassLikeNode` interface, because an anonymous class is not a statement; it declares `$name` (null for the anonymous one) and `$members`. The five kinds written with parameters and a body implement `FunctionLikeNode` for the same reason, declaring `$openParen`, `$parameters`, `$closeParen` and `$returnType`, null where a property hook has none; the two written as expressions, `ClosureNode` and `ArrowFunctionNode`, implement `AnonymousFunctionNode` beside, a `FunctionLikeNode` with the `$staticKeyword` they share. Every declaration that may carry attributes (a member, a constant, an enum case, a parameter and the class-like and function-like ones, whose interfaces extend it) implements `AttributeAwareNode`, declaring `$attributes`, because they share no base class. `findAncestor()` and `find()` return them intersected with `Node`, so a result is still a node to search in.
- A `VariableNode` is a variable being used, so a rule about variables can take every one of them: the name of a static property is written the way a variable is (`A::$b`, `A::$$b`, `A::${expr}`) but is a name, and `StaticPropertyFetchNode` holds the `dollar`, `openBrace`, `name` and `closeBrace` of that writing in slots of its own, `$plainName` giving the name without the dollar. The `$b` of `A::$$b` is a `VariableNode` again, because that one is read. A variable that is being declared rather than used is a `VariableNode` too, in the `variable` slot of `ParameterNode`, `CatchNode`, `ClosureUseNode` or `StaticVariableNode`. So is the bare name of `"${name}"`, whose token carries no dollar, which is why the name of a variable is read as `$plainName` and not from the text of its token.
- An expression written with an operator implements `OperatorNode` and says through `$precedence` how tightly it binds, in the order of the precedence declarations of the grammar, whose numbers mean nothing but that order, and through `$associativity` which side it leans to. One written with no left operand, whose right one reaches as far as the code lets it, implements `RightExtendingNode`, an `OperatorNode` itself: an arrow function, throw, print, yield, yield from and include capture nothing before themselves, so where nothing follows them they stand bare however loosely they bind. `ParenthesizedNode::isRedundant()` reads that from both sides of a pair of parentheses and answers whether they may go, and no where it is not certain. What follows them is not only what stands beside them: it is the next token of the nearest ancestor they do not end, so `$a + (yield $b) + 1` keeps them although the yield ends the sum it stands in. And what would take it is not only the expression in them but whatever operator ends it: a prefix operator (`!`, `-`, `@`, a cast) captures nothing before itself either and takes what binds at least as tightly as itself, so `(bool) (!$a)` loses them and `(!$a) instanceof B` keeps them, and `(@include $f) !== false` keeps them for the include inside. Precedence is not all it asks: a pipe takes an arrow function in parentheses only, and `::` takes the name of a class on its left, so the parentheses of `(FOO)::class`, `(FOO)::BAR`, `(FOO)::m()` and `(FOO)::$p` are what makes the name an expression, `FOO::class` being the name `FOO` itself and `(FOO)::class` the class of what the constant holds; `true` and `null` are written as names too, while anything else there is an expression either way, and `->` and `[]` take one whatever stands before them.
- `ExpressionNode::toValue()` gives the value an expression is written as, a scalar, null, true, false or an array of them, and throws where it is written as none, which `hasValue()` asks beforehand. A name is not a value: what it stands for is a matter of what the code around it defines.
- The layout role of a slot (`LayoutData`, generated from `grammar/nodes.php`: the convention by the name of the slot, `layout` where the schema says otherwise) says what the slot is to the indentation of the lines the node spreads over, which is what a tool laying out code by the tree alone counts from.

## Analyses

An analysis is information derived from a file: `NameResolver` (namespace, imports, resolution of class, function and constant names with the runtime fallback of unqualified functions and constants to the global namespace, `resolve()` choosing among the three by the `$symbolKind` of the name, `isGlobalFunctionCall()` and `findGlobalFunction()`, which tells which of a set of global functions a call calls, as the set writes it, a map keyed by the names among them, the name a declaration introduces and the declaration of a name (`getDeclaredName()`, and `findDeclaration()`, which looks among the symbols of one `SymbolKind`, PHP keeping a class, a function and a constant of one name apart, in the declarations collected once for the file, so it costs a lookup and gives the first declaration of a name the file repeats), and the way back: `shortenName()` gives the shortest way to write a fully qualified name where a node stands, through an alias, a prefix import or the namespace, and `isAliasFree()` says whether a name is still free there, which is what adding an import asks) and `Scope` (availability of `$this`). The enclosing function-like construct and class need no analysis: they are `findAncestor(FunctionLikeNode::class)` and `findAncestor(ClassLikeNode::class)` of a node or of a token, whose `findAncestor()` starts at its parent.

An analysis that derives something from the whole file takes the `FileNode` in its constructor and keeps what it has read, `NameResolver` among them, and reads it anew once `FileNode::$revision` says the tree has changed, so a caller that mutates the tree keeps the analysis and never gets an answer mixed from two versions of the tree. `Scope` keeps nothing and takes nothing, every question being answered by walking the parents of the node it is given, so it outlives any mutation.

Imports belong to the namespace block they are written in, a declaration to the namespace itself, so a second `namespace A {}` block of the same file sees what the first one declared and none of what it imported; a declaration inside a condition or a function body counts too, as the declaration the name resolves to, but PHP declares it only once that code runs, so such a name is uncertain (`UnqualifiedResolution::Uncertain`) and `shortenName()` writes it qualified. An unqualified function or constant declared in another file is invisible to the file, so the resolver takes such a name as global unless the `NamespacedSymbols` given to the constructor list it; whether the list says it is complete decides only how certain that answer is. `getUnqualifiedResolution()` tells such a name taken as global (`UnqualifiedResolution::Uncertain`) from one known to be (`Global`) and from one reaching a symbol of a namespace (`Namespaced`), the question a tool rewriting a call of a global function asks before calling the rewrite safe; it takes an unqualified name only, since no other name falls back, and `Global` says that the name reaches the global namespace, not that it reaches the symbol it spells, which an import may rename; a `NameNode` given brings its kind and its place, a string needs both. `shortenName()` writes a function or a constant bare only where the bare name reaches it for certain.

A node from another tree is refused, not answered in the global namespace, because a valid answer to a question nobody asked is worse than an exception, and so is a name that refers to no symbol (`NameNode::isReference()`): `int` in a type, the name a `use` introduces; self, static and parent come back as they are. `resolveClass()`, `resolveFunction()` and `resolveConstant()` take `$at` for the node the name is to be read at, which is what a name lifted out of the file into a copy needs, as `shortenName()` and `isAliasFree()` do.

## Parents, mutation and the index

- A node or token belongs to exactly one tree: `$parent` is set by the parser and by the mutation API, and inserting a node that already has a parent throws. Two values may have one. A node standing inside the child the write releases (`$assign->expression = $binary->right`), which is how an operand is taken up in place of what holds it. And a node standing in a subtree whose root is not a `FileNode`, where no index can come apart over it, so a codemod replaces a call and then takes out of it what the replacement needs, and a fragment gives up a part of itself. What is left of either still points at the value, so it is waste and not material, and whoever wants it whole clones it before the write; a value taken this way carries the trivia of the place it came from, the way a clone does, and `setEdgeTrivia([], [])` clears them. A child of the node doing the write is taken from nowhere, because taking it from itself would put it in twice. `clone` gives a deep copy without a parent, over the slots and the items of the lists; it is the one walk of the library that recurses, so a nesting tens of thousands of levels deep, which the parser, the printer, the index and the traverser take in their stride, stops it at the stack limit of PHP.
- A slot is a public hooked property, written by assignment (`$node->condition = $expression` or `replaceChild()`): the set hook the generator writes (`set => $this->prepareSlot(__PROPERTY__, $value)`) calls `Node::prepareSlot()`, which refuses a value that has a parent, adopts it, releases the current one and reports `structureChanged()`, and returns the value the hook writes; a node standing nowhere only sets the parents, having no file to report to, and asks about the value only where it may stand elsewhere or hold the node. `FileNode`, the one node without a parent that has a file, writes its slots its own way. A slot that may stay empty is declared `= null` and the constructor skips an empty one, so building a node runs no hook for what the code does not have. The type of the property is what refuses a value that does not fit, before the hook runs. The rest of the mechanics live once in `Node`, over the `Slots` constant every node class carries (its slots in source order): `getChildren()`, `getFirstToken()`, `findSlotOf()` and `replaceChild()`. The hooks run in the constructor too, so a node adopts its children as it is built; the handwritten lists, which have no `Slots` and read their items themselves (their first and last token and the helpers they share come from `NodeList`), adopt theirs in the constructor the same way, so a node is never built and attached in two steps.
- Writing what a place already holds does nothing: a slot assigned its own value, `replaceChild()` with the same child, `replaceWith()` of the node itself and the trailing separator a list already has change neither the tree nor `FileNode::$revision`, and neither do the text a token or a name already has, the value a string literal already reads as in its delimiter (`StringNode::setValue()`, whatever the escapes it is written with), the trivia a token already has (the same array, its very trivia, since a mutation finds one by identity) and the whitespace a helper finds already written, so a generic transformation may give back the node it was handed and a pass that changes nothing leaves the analyses of the file valid; the same node written into another place is still refused.
- Everything a write refuses, it refuses before it moves anything: `Node::checkValue()` refuses a value that holds the node written into, which would make a cycle, and one standing where the write may not take it from, and moves nothing, and `Node::prepareValue()` checks a value and then frees it, for every write, the lists and `ModifiersNode` among them. A write of several values, an item with its separator, checks all of them before it frees any, and refuses values that overlap, a separator taken out of the item it is to separate, which would stand in two lists at once. So a refused write leaves every tree it was given exactly as it stood, trivia and all, the fragment a value came from included, and `replaceWith()` moves the trivia of the old node only after the parent has taken the new one.
- Lists mutate through `append()`, `insert()`, `removeItem()`, `replaceChild()` (`removeItem()` and `ModifiersNode::removeToken()` are named apart from `Node::remove()`, which removes the node itself, because PHP forbids an incompatible signature in a child class); `SeparatedNodeList::insert()` derives a missing separator from the existing ones (or `", "` in a one-line list) and gives the item the indentation of its neighbor in a multi-line list; a separator carrying a comment models nothing, the comment being content that a copy would duplicate, so the next separator stands in for it, `removeItem()` takes the separator after the item, or before the last one (`findSeparatorOf()`), and the item goes with all its trivia, comments included, tidying no line; that is what `Node::remove()` adds. `PlainNodeList::insert()` models the neighbor too, there being no separator between statements to carry the line ending: an item that carries no trivia of its own takes the indentation of its neighbor and ends its line the same way, as long as the list stands in a file and the item does not end its line inside its own text, as a close tag and inline HTML do. A statement ended by a close tag leaves the tag behind as an `EmptyStatementNode`, because the tag ends the code and without it the text after it would be read as code; a statement opening its code too (`<?= $a ?>`) goes whole, and so does the empty statement of a close tag, whose removal is for the caller to decide. After a close tag and inline HTML whatever is written is output of the script, so `remove()` gives no trivia to such a token, the comments and the whitespace going to the next one, after its open tag. The constructors of the lists, internal and fed by the parser with fresh nodes, adopt their children one by one and promise none of this.
- `Node::remove()` removes a list item together with the separator that goes with it: a node alone on its lines takes the lines with it, otherwise the whitespace around stays, the gap the separator opened goes with it and whatever is left dangling before a line ending is trimmed; its comments, each with the line ending after it and the whitespace indenting it, a comment that shared the line of a node alone on its lines standing on a line of its own and one staying within a line followed by a space, go to the next token, right after the previous token (to the next one where there is none), or out of the tree with the node, as the `CommentPolicy` says. Those are the comments the node owns: the ones inside it and on its line, the block of comment lines right above it and the block holding its doc comment, which PHP reads as the documentation of the node across a blank line too, so the header of a file written as a doc comment right above a class is the documentation of that class. The comment lines above them, set apart by a blank line or standing on the line of the open tag, are a preamble, the header of a file or of a section, which belongs to no node and stays where it stands with the blank lines below it, whatever the policy. A node goes without the comments the tree keeps, its edges cleared and the comments inside it removed (`MoveToNextToken`, `MoveToPreviousToken`), or with the ones it owns and the indentation of its lines (`StayWithNode`), so that `remove()` with `StayWithNode` and an insertion elsewhere move a node with its documentation and nothing else; in a subtree without a file, where no token around takes them, it keeps them all. The default keeps every comment in the tree, so a doc comment of a removed declaration becomes that of whatever follows it, and a caller to whom that is wrong refuses such a node or takes the comments out with it. Whatever the policy, the trivia left between the token before the node and the one after it are split between the two as the lexer splits them, so `getTrailingSpace()`, `startsLine()` and `countBlankLinesBefore()` answer as after a reparse, and the same holds where `replaceWith()` gives them to the tokens around. `Node::replaceWith()` keeps the trivia around the old node around the new one by joining them with the new node's own edge trivia, or, where the new one has no token to hold them (an empty list), gives them to the tokens on either side as the lexer would place them, the previous one up to its line ending and the next one the rest, and refuses before any write where there is neither, and `Token::replaceWith()` does the same for a token, which is how a token changes its kind; a replacement cloned from nearby source still carries its original leading trivia, so clear the clone's edges first or an `OpenTag` gets doubled. A replacement may also come to stand right against a token it would be read together with, `'a'.` against `119`, `return` against `FOO`, `-` against `-$a`; `replaceWith()` asks the lexer about the two seams (`Lexer::canAdjoin()`, which whoever takes whitespace away from between two tokens asks as well) and puts a space where the pair reads as something else without one and as itself with one, in a subtree without a file too. Writing a slot by assignment does not ask.
- Where a property is written and where a method is, is decided by how many values the write takes. A property is read whenever the answer is derived from the tokens (`value`, `base`, `quote`, `label`, `indentation`, `form`, `parts`, `symbolKind`, `text`), a boolean among them where it tells a state written in the code and an adjective names it (`static`, `final`, `readonly`, `nullsafe`, `promoted`); a boolean is a method where it judges what the code means (`isRedundant()`, `isWritable()`), where its name would be a noun (`isGroup()`, `isConstructor()`), where it narrows a slot with `@phpstan-assert-if-true` (`isOfThis()`), and where a collection answers it (`isEmpty()`). A property is written when the write takes exactly one value and has one consequence: the slot of a node, and `NameNode::$text`, whose hook tokenizes the name anew. A method writes when the write takes more than one value or when two things must change together, because two properties would mean that writing one reads the other and the caller has to think about the order: `StringNode::setValue($value, ?$quote)` is that case, the delimiter deciding how the value is written. The text and the trivia of a token are methods for a third reason: `?->` cannot stand on the left of an assignment, so `$node->getFirstToken()?->setText('x')` has no property form. `Token::setText()`, `setLeadingTrivia()` and `setTrailingTrivia()` do for a token what the hook of a slot does for a node, and `Node::setEdgeTrivia()` writes the trivia on the outer edges of a node, where the first or the last token may be missing. The parser goes through the same setters on tokens that are not in a file yet, where there is no index to tell; the lexer, which makes the tokens, writes their trivia directly from within `Token`.
- What neither a hook nor a setter covers the language guards instead: the trivia of a token are `private(set)`, the items of a list are its own storage, written by its methods alone, and the `parent` of a node is `protected(set)`, which is why no PHPStan rule watches the tree. The text and the kind of a token and the text of a trivia are properties of `PhpToken`, which a child class can neither narrow nor hook, and inheriting them is what keeps the lexer fast, so only the contract guards them: the text is written by `setText()` alone and the kind never, and writing either directly is not supported; `PhpToken` being the parent is no part of the API, whose members are those `Token` and `Trivia` declare, `line` and `pos` among them, and of the inherited methods `is()` alone, which compares the kind or the text; the inherited `tokenize()` gives the raw tokens of PHP, not those of `Lexer::tokenize()`. The parent is `PhpToken` for speed: composition would guard the writes, at the cost of an object more for every token the lexer makes. `Token::$parent` and `Trivia::$inInterpolation` are public for the same reason, written by the tree and by the lexer alone. The `parent` of a token is public, written by the tree alone, so that a node writes it without a method call, as it writes the parent of a node. A `private(set)` array takes no indirect change from outside, so `end($token->trailingTrivia)` needs a copy.
- The setters are what keeps the index right: `FileNode` owns the `TokenIndex` (order, previous/next token, offset, line, column, visual column) built lazily and kept up to date rather than rebuilt; the index is `@internal`, what it knows being asked of a token (`getCurrentLine()`, `getNext()`, `isBefore()`...), so that it may change as the speed asks. A structural change reports the children it adopted and released and `structureChanged()`, and the index moves their tokens at its next query, when the tree has its new shape whatever the order of the writes, so a run of writes costs one move; a token setter reports `tokenChanged()` with the line endings the token gained or lost, and the positions before the token stay as they are. The numbering, the lines, the offsets, the columns and the visual columns (for the tab width last asked about) of the tokens after a change are brought up to date lazily, as far as the queries reach, so the cost of a change of text or trivia followed by a query nearby is proportional to the distance, not to the file; a structural change adds the move, which shifts the tokens after it and so costs in proportion to the file, unless a child takes the place of a released one with as many tokens, which is written over it and moves nothing. A tree changed behind the back of the index is a `LogicException` once the index reads its order again, not a slow path, and so is a subtree entering a file with a child a write took out of it, which would otherwise stand in the order twice. Every mutation increments `FileNode::$revision`, which is how a caller detects one. A token carries its ordinal and the index that numbered it (`Token::$ordinal`, `Token::$indexedBy`, both `@internal`), which is how navigation finds the file without walking the parents; the shortcut is verified against the index before use, so a token moved to another tree falls back to the parents. Navigation from a detached subtree returns `null`.
- `Token::$line` and `$pos`, the properties of `PhpToken`, never change and are the source of positions in reports, -1 for a token that did not come from the lexer and for one the lexer read without positions (`withPositions: false`, a fragment), the end of the file among them; `getCurrentLine()`, `getCurrentColumn()` and `getCurrentOffset()` follow mutations. A `Trivia` has the same `$line` and `$pos`, where it stood in the source it was read from.
- A node reads its own text and its own edges: `$text` is what is written between its first and its last token, the trivia on the outer edges left out, which is what a report prints, while printing the node writes those edges too, as the round trip needs; `$leadingTrivia` and `$trailingTrivia` are those edges, and `setEdgeTrivia()` writes them. `getTokens()` gives the tokens of the whole subtree in source order.
- A single trivia (typically a comment) is removed by `Token::removeTrivia()`, which tidies the whitespace around it: one alone on its line takes the line with it, an inline one takes an adjacent space; `Token::replaceTrivia()` swaps one in place. A node does the same for a trivia of any of its tokens, or of the one before it where a doc comment of the node may stand (`Node::removeTrivia()`, `Node::replaceTrivia()`), which is what closes the way from a comment found on a node to the mutation removing it. A doc comment is read with `Node::getDocComment()` (above the node, or after the previous token) and written back with `Node::replaceDocComment()` or dropped with `Node::removeDocComment()`; what a doc comment says is for the caller to parse, the tree only carries its text. A `Trivia` is never changed once made, so the same instance may sit on several tokens, and a mutation naming one finds it among the trivia by identity; `withText()` makes a copy with another text, which keeps the position, standing where the original stood.
- Comment queries for whoever must not destroy a comment: `Token::hasComment()` (in the trivia of the token), `Token::hasCommentUpTo()` (anywhere between the texts of two tokens of one file, in their order, refusing any other pair, since a guard of comments answering no to a question it could not ask would destroy one) and `Node::hasInnerComment()` (inside the node, its outer edges excluded), beside `hasLeadingComment()` and `hasTrailingComment()` of a node (on its outer edges) and of a token (on either side of its text, which `hasComment()` asks of both at once); `Token::getComments()`, `Node::getInnerComments()` and the `getLeadingComments()` and `getTrailingComments()` of both give what those count. A comment is inside a node, before it or after it, and a node asked for all three composes the three. A `Trivia` says of itself whether it `isLineComment()` or `isMultiLineComment()` and hands over its text without the delimiters as `getCommentText()`. The queries of a node walk its own tokens and need no index, so a subtree taken out of the tree answers as it did inside it.
- `Node::matches()` compares two nodes by their token texts (`getTokenTexts()`, which is also what a tool keys a map by where the layout must not count; the size of code is measured on `$text`, which keeps it), `ExpressionNode::isRepeatableRead()` tells whether reading an expression again is free of side effects; together they answer "does this assignment repeat its target". That answer is syntactic: a magic getter or a hook behind a fetch, an `ArrayAccess` behind an offset and a `__toString()` behind an interpolated string are out of its sight, and whoever cannot assume that much needs the types, which a syntax tree does not have.
- `ExpressionNode::getDereferenceKind()` tells how the parent reaches into the expression, as a `DereferenceKind` (`Fetch` for `->` and `[]`, the call of a method included, `Call` for `(...)`, `StaticAccess` for `::`) and null where it does not reach in at all, which `isDereferenced()` is the same question asked without the kind; `isDereferenceable()` answers the other way round whether what is written after the expression may reach into it with no parentheses around it, which differs by what that is and so takes the same enum, `canNameClass()` whether it may stand where a class is named, and `isWritable()` whether it may stand where a place is assigned to, which a `?->` anywhere in the chain the write reaches through rules out, a call in the chain included, and so does a chain starting at a value of its own, a literal, a constant, `new` or `clone`, the way PHP refuses both; `ParenthesizedNode::isRedundant()` asks all of them along with the precedence of both sides.
- Horizontal whitespace between two tokens on a line is the trailing trivia of the first one, never the leading trivia of the second (whoever joins two lines writes the space there, or the next reader of the gap sees none), and it is read and written through `Token::getTrailingSpace()` and `setTrailingSpace()`, which return or refuse `null` when a line ending, a comment or string content is in the way, or when the first token ends its line by its own text (a close tag, a heredoc start); `Token::is()` is the one of `PhpToken`, which compares a text given it with the text of any token, the content of a string included. `Indentation::measureLineWidth()` measures the line of a token visually, a tab moving to the next stop of the style wherever on the line it stands, which is the same counting `getVisualColumn()` does and what the reader sees; any other character counts as one, a wide or a combining one too, the terminal cells being no concern of a syntax tree. The line is the physical one, which may start and end inside a token or a comment, and a token spanning lines is measured on the line it starts on. `Token::removeTrailingWhitespace()` takes away the whitespace the trailing trivia end with, which in the middle of a line is the space before the next token, so the two come to stand together and `Lexer::canAdjoin()` is not asked; it also trims the end of a `//` or `#` comment, because the tokenizer counts the spaces before the line break as part of the comment text; a caller therefore changes a comment by it.
- A mutation keeps the trivia canonical: the line ending that ends the line of a token belongs to that token's trailing trivia, never to the leading trivia of the next one. A misplaced one makes `getTrailingSpace()` blind to the line break; `ensureStartsLine()` and `setBlankLinesBefore()` place it correctly, so build on them. The helpers writing whitespace (`setTrailingSpace()`, `setIndentation()`, `ensureStartsLine()`, `setBlankLinesBefore()`, `Indentation::set()`) refuse before they write what would break that: whitespace within a line that is not spaces and tabs, a line ending other than `\n`, `\r\n` and `\r`, a negative count; `setLeadingTrivia()` and `setTrailingTrivia()` write what they are given.
- The whitespace conventions of a file are a `Style`: the indentation unit, the line ending (`Style::detectLineEnding()` reads the prevailing one) and the width of a tab, which is what visual columns and line widths count with.
- Indentation is changed through `Indentation` (`set()` a line and the comments above it, `normalize()` into the characters of the style) and `Token::getLineIndentation()`; `Token::setIndentation()` alone moves one line and leaves the rest of the statement where it was. `Indentation::findOwner()` tells which construct a line-opening token continues and in what role, as a `LineOwner`, and `Indentation::infer()` gives the indentation such a line conventionally has, counted from the line its construct begins on. `Indentation::opensLine()` says whether the line ending above a token is trivia, which is the only case its indentation is whitespace to write: `Token::startsLine()` also answers yes after inline HTML, a heredoc body or a close tag, and there the leading whitespace is text. `Indentation::shift()` moves every line a node opens by a level, and with them the body and the closing delimiter of a heredoc, which keeps the value it stands for; inline HTML and the content of a string are text of their own and stay.
- `Node::getChildren()` is the children in source order, empty slots left out, and the only way to the children: a node is not iterable, so that there is one way and it is an array, which the printer, the index and the traverser read directly. `Node::find()` takes a class and a predicate that narrows it, and gives the descendants of that class the predicate accepts as a snapshot safe to iterate while mutating, `Node::findFirst()` stops at the first one; the class may be an interface node classes implement, as it may for `findAncestor()`, and the predicate gets the node typed, so a slot of it is reached without an instanceof. The `Traverser` walks in pre-order with the static `traverse($root, $enter, $leave)`, a callback steering it with `TraverseAction::SkipChildren` or `Stop`, a case of an enum so that no value a callback returns of its own steers it, and it keeps its state in the walk, so a callback may start a walk of its own; it leaves every node it entered, so a callback keeping a state of its own stays right; it does not descend into a replaced node, skips siblings detached meanwhile and leaves inserted ones for the next walk. A node the walk hands over may therefore be one a callback has already taken out of the tree, which its `parent` says (null for anything but the root), and whoever passes the nodes on to somebody else filters by that, because `replaceWith()` and `remove()` throw on a node outside the tree, and a write into one changes what no file prints.

## Garbage collection

A tree is cyclic, every child pointing to its `parent`, so a tree dropped by the caller is freed by the cycle collector, not by reference counting, and the collector scans the tree it meets. During the parse of a large file it runs repeatedly over the growing tree: on files of hundreds of kilobytes it takes 20–40 % of the parse, while a file below some 40 kB seldom sets it off. The library leaves the collector alone, because the moment to collect is when a tree is dropped, which only the caller knows. A tool going through many files may switch the collector off while it works on a file and call `gc_collect_cycles()` once it is done with it: that saved 8–11 % on typical code and a third on files of data, memory staying the same. Switching it off without collecting after each file only looks faster, the garbage is then never collected.
